## Directory layout

- `~/.config/lasa/{primary,review}/` holds each role's `1.0.0` `config.json` and separate `authorization.json`.
- `~/.config/lasa/secrets/{primary,review}/` supplies model and TLS files. Primary also reads its issuer JWKS here.
- `~/.config/lasa/registries/review/static-tokens.json` holds the static-token digests, subjects, and expirations. Update the registry from an administrator environment using the token issuance command. [Static tokens](../RUNNING.md#static-tokens)
- `~/.local/state/lasa/{primary,review}/` holds the derived `private/` and `workspaces/` directories. Each supervisor has one writable state mount.
- `~/.local/share/lasa/connectors/` provides the filesystem MCP executable and `~/.local/share/lasa/documents/` contains its approved source files. Primary mounts both read-only.
- `~/.local/state/lasa/archives/pre-1.0.0-20261123/` contains the verified `primary/state.tar.gz` and `review/state.tar.gz` archives, their checksums, and archived predecessor deployment files.
- `~/.local/state/lasa/archives/pre-unified-1.0.0-20261123/` holds the earlier verification stores and their manifests and policies. Those stores used SQLite schema revision `1`.
- `~/.local/state/lasa/releases/1.0.0/typed-workflows/<role>/predecessor/` holds the prior config and policy for the stopped `lasa-primary-pre-typed` and `lasa-review-pre-typed` containers.

## Verified consumer API rollout

On November 25, 2026, primary and review moved to `consumer-api-20261125-6121eeb73c44`. Each role runs its own supervisor and launcher, uses a dedicated launcher socket and schema-3 store, and mounts its own policy and credential paths. The primary supervisor mounts the approved documents and connector executable read-only. The launchers hold Docker daemon access.

Both roles share the air188 host, kernel, Docker daemon, `lasa-supervisors` bridge, HTTPS ingress, and inspection stack. Host and Docker administrators can access both roles. JWT and static-token authorization, role-specific state, and separate mounts enforce the application and container boundaries on this shared infrastructure.

The isolated canary and production HTTPS checks verified the Mac's static-token review request, JWT checklist request, and approved `documents.read`. The Mac verified the review before approving its exact disclosure to the checklist receiver. Separate consumer and operator captures are stored in private release evidence. The predecessor containers and stores were retained with verified rollback snapshots.
